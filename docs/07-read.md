# 实验七：按需拉取

**实验目标**　支持 READ opcode：由需要数据的一方主动从远端拉取指定范围。实现复用实验三的切片逻辑，但字段含义与完成语义相反。

**教材**　[2.8 RDMA READ 操作](https://renfeng.org/RDMA101/02-programming-model/08-rdma-read/)，其中 [2.8.2 RDMA READ 的完成语义](https://renfeng.org/RDMA101/02-programming-model/08-rdma-read/)、[2.8.3 最大并发 RDMA READ 限制](https://renfeng.org/RDMA101/02-programming-model/08-rdma-read/)、[2.8.5 错误处理](https://renfeng.org/RDMA101/02-programming-model/08-rdma-read/)

**前置**　完成[实验四](04-window.md)：Engine 已有切片与在途窗口。

## 背景

前面几个实验里，数据都是由"有数据的一方"推出去的：WRITE 把本地数据写到远端，SEND 把消息发给远端。但有时需要数据的是另一边，而数据恰好就在对端内存里——比如本地缓存缺了一块，只有自己知道缺哪一块。这时由需要数据的一方发起 READ，把远端范围拉回来，比让对端主动推送更合适。

### 方向反过来，字段含义也跟着变

READ 和 WRITE 共用同一种请求类型（C 的 `r101_request`、C++ 和 Rust 的 `Request`），因为两者都描述"本地一段 + 远端一段"。区别只在方向，而方向反过来，几个字段的意思就变了：

| 字段              | WRITE                      | READ                           |
| ----------------- | -------------------------- | ------------------------------ |
| `local_address`   | 本地源，任务完成前不得修改 | 本地结果区，任务完成前不得读取 |
| 远端 MR 所需权限  | `REMOTE_WRITE`             | `REMOTE_READ`                  |
| 数据流向          | 本地 → 远端                | 远端 → 本地                    |
| 是否消耗远端 RECV | 否                         | 否                             |

### READ 还占用对端的响应方资源

WRITE 和 SEND 都不需要远端为未完成的请求保留状态。READ 不一样：请求发出后，远端要把数据发回来；在这段时间里它扮演的是这次请求的**响应方**，必须为每个还没完成的请求留一份状态——这份状态就是通常说的**响应方资源**（responder resources）。`max_rd_atomic` 限制本地能同时发起多少个，对端的 `max_dest_rd_atomic` 限制它愿意同时接受多少个，两者在 QP 迁移到 RTR / RTS 时设置（教材 2.8.3）。超过对端的限制，完成状态就是 `REM_OP_ERR`。

所以 READ 的在途数量不能只看发送窗口：发送窗口管"投了多少条 WR"，响应方资源管"对端愿意同时为多少个未完成请求保留状态"，两者都要管。

## 实验内容

### 范围与边界

**实验边界：** 实验七只要求支持 READ：由需要数据的一方主动从远端拉取指定范围。实现上可以缩小为单个 peer、单个后台 worker、单个 CQ。

**不在本实验范围内：** 用多条 QP 分摊 READ 负载；QP 出错后的重连与恢复。

## 实现要点

**1. 切片复用。** 切片算法与 WRITE 相同，区别在于本地地址推进的是目的地址、远端地址推进的是源地址。约束不变：两个地址同步推进，覆盖完整范围，尾片单独处理。

**2. 结果可用。** READ 的 CQE 到达时数据已位于本地缓冲区，因此该任务的 COMPLETED 就是"结果区可读"的时刻。与 WRITE 相反，本地内存是结果而非源。

**3. 权限方向。** READ 需要远端 MR 的 `REMOTE_READ`，以及本地结果区的 `LOCAL_WRITE`；它不需要 `REMOTE_WRITE`。校验不通过时应在接受前拒绝，或让任务以 FAILED 结束，而不是让设备产生一次越权访问。

**4. 并发窗口。** READ 的在途数量除受发送窗口约束外，还受 `max_rd_atomic` 与远端 `max_dest_rd_atomic` 约束。Engine 需要自己把在途 READ 限制在这个上限内：应用一次提交的 READ 可以远多于 `max_rd_atomic`，但设备不应收到超过上限的并发请求。

## 验收

实验七的测例会按下面的要求检查你的 Engine 行为：

| 编号 | 场景与输入                                                                                         | 预期行为                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| L7.1 | 一次提交若干 READ，本地结果区与远端源区偏移各异、长度不一，两侧都带保护区                          | 全部 COMPLETED；拉取到的数据逐字节正确；本地结果区的保护区不变，远端源区的内容也不被修改                                     |
| L7.2 | 单独提交零长度 READ；再提交长度覆盖边界（短于切片、跨多片、带余数）且远端起始地址带非零偏移的 READ | 零长度 READ 直接完成，不需要注册或导入内存；其余 READ 数据正确，结果范围精确等于 `[起始, 起始 + length)`，范围外的保护区不变 |
| L7.3 | 远端 MR 未授予 `REMOTE_READ`，提交一条 READ                                                        | 任务以 FAILED 结束或提交被拒绝，不产生越权读取，也不崩溃                                                                     |
| L7.4 | 本地结果区没有 `LOCAL_WRITE`，提交一条 READ                                                        | 任务以 FAILED 结束或提交被拒绝，不产生越权写入，也不崩溃                                                                     |
| L7.5 | 一次提交的并发 READ 数量远多于对端允许的上限                                                       | 全部 READ 成功，没有请求因 `REM_OP_ERR` 失败，也没有任务永久停在 PENDING                                                     |
| L7.6 | 同一批混合 READ 与 WRITE                                                                           | 两条任务的完成各自正确：WRITE 目标区与 READ 结果区都逐字节正确，保护区不变                                                   |
