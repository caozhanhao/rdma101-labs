# 实验五：批量投递与选择性信号

**实验目标**　降低每次投递与每次完成的固定开销：把多个 WR 连成链表一次投递，一次轮询取回多条完成，并只让部分 WR 产生 CQE。

**教材**　[2.4.7 示例代码：批量投递](https://renfeng.org/RDMA101/02-programming-model/04-qp/)、[2.4.3 CQE 生成的控制](https://renfeng.org/RDMA101/02-programming-model/04-qp/)、[2.5.4 示例代码：批量轮询](https://renfeng.org/RDMA101/02-programming-model/05-cq/)、[2.5.6 不同操作的完成语义](https://renfeng.org/RDMA101/02-programming-model/05-cq/)

**前置**　完成[实验四](04-window.md)：发送窗口已经可用，多条 WR 同时在途，配额凭 CQE 归还。

## 背景

实验四的发送窗口让设备忙了起来，但每一次投递和每一次完成还是"一条一条"处理的：一条 WR 一次 `ibv_post_send`，一个 CQE 一次 `ibv_poll_cq`。WR 一多，这些固定开销就跟着线性增长。本实验把这两个动作改成批量执行，同时仍要能准确判断哪些 WR 在途、哪些已经完成。

### 投递、轮询与信号

实验四里每个 WR 都要单独投递、单独取回完成，信号也是每条都单独处理。但 verbs 对投递、轮询和信号都提供了批量形式：

| 动作     | verbs 提供的机制                                     |
| -------- | ---------------------------------------------------- |
| 投递 WR  | WR 链表一次投递（`wr.next`）                         |
| 轮询完成 | `ibv_poll_cq` 一次取回多条 WC                        |
| 产生通知 | `sq_sig_all = 0`，仅部分 WR 设置 `IBV_SEND_SIGNALED` |

要用上这些机制，Engine 需要自己决定：一次投多少个 WR、一次取回多少条完成、每隔多少条 WR 设置一次信号。本实验把这三个量分别叫做 `post_batch`、`poll_batch` 和 `signal_interval`。

### 选择性信号：完成证据变成一段前缀

选择性信号意味着不再每条 WR 都产生 CQE：只有设置了 `IBV_SEND_SIGNALED` 的那些才会。那没设信号的 WR 完成了没有，怎么判断？靠 SQ 的顺序性——SQ 按顺序处理请求，一条 WR 完成时，排在它前面的 WR 一定也已经完成。所以，一条带信号的成功 CQE 到达，就同时证明了同一 SQ 上排在它之前、没有单独产生 CQE 的 WR 也都已经完成。它证明的不是单独一条 WR，而是从最老的未完成请求到它自己这一段连续的**前缀**（教材 2.5.6）。

这直接改变了记账方式：归还配额的单位从"一条 WR"变成"一段前缀"。一条 CQE 可能归还多个配额，而这些 WR 分属不同任务，任务状态要按各自的进度分别推进。

### 投递失败只发生一半

`ibv_post_send` 从链表头开始一条条投递，一旦某个 WR 投不出去（本身不合法，或者 SQ 已经满了），它就停止继续投，并把第一个投失败的 WR 通过 `bad_wr` 返回。注意这时的状态不是"全都没投出去"：**`bad_wr` 之前的 WR 已经进了 SQ，仍会正常执行**。于是投递失败要分两段处理：

- `bad_wr` 之前：已经在途，要记入配额、等完成证据；
- `bad_wr` 及其之后：还没进 SQ，等 worker 稍后把它们重新连成链表再投。

整体重投会让前一段执行两次，整体丢弃则会让配额永远收不回来。

## 实验内容

### 范围与边界

**实验边界：** 实验五只要求把"每条 WR 单独投递、每条完成单独回收"改为批量：按 `post_batch` 把待投递的切片连成链表一次 `ibv_post_send`，按 `poll_batch` 一次取回多条 WC，并按 `signal_interval` 只让部分 WR 产生 CQE。可以缩小为单个 peer、单个后台 worker、单个 CQ、单个 SQ，不引入新的公共接口。

这几项机制的目的都是性能优化：减少每条 WR 的固定投递开销和每条完成的固定回收开销。但本实验**不要求你把优化效果测出来**——测例跑在 Soft-RoCE（RXE）上，它的耗时与带宽不代表真实网卡，设阈值没有意义。三个策略参数取多少由你决定。

**不在本实验范围内：** 故障恢复与连接重建，包括错误让 QP 进入错误状态后的处理；错误 CQE 之后的重试；多 QP、多 CQ、多后台 worker。

## 实现要点

**1. 链式投递。** 按 `post_batch` 把待投递的切片连成链表，一次调用 `ibv_post_send`。链上的每个 WR 仍有各自的 `wr_id` 与 SGE，链表只改变投递方式。

**2. 部分投递的处理。** 投递失败时按 `bad_wr` 划分：之前的 WR 视为已投递，记入配额并等待完成证据；`bad_wr` 及其之后的 WR 视为未投递，等 worker 稍后重新连成链表再投。

**3. 选择性信号。** 按 `signal_interval` 设置信号。注意以下情形必须提前设置信号，否则配额无法归还：链表末尾；窗口小于信号间隔；一个 batch 的最后一片。

**4. 前缀回收。** CQE 到达时，同时回收该 CQE 所证明的那段前缀，并按相同粒度推进任务状态：一段前缀里的每个 WR 可能属于不同的任务，不能只推进其中一条。

**5. 尾部收尾。** 任务较短、最后不足一批、窗口小于信号间隔时，都需要显式的信号才能产生完成证据。窗口与信号间隔的组合需要在实现中逐一检查，避免任务永久停在 PENDING。

## 验收

实验五的验收既看搬运结果，也看批量化是否真的生效：多 WR 的批次应链成链表一次投递、一次取回多条完成，并且只有部分 WR 产生 CQE。

单条 WR 的短批次只要正常完成即可，不要求它体现批量或减少 CQE。批量大小、信号间隔与窗口大小都由实现自己决定。

实验五的测例会按下面的要求检查你的 Engine 行为：

| 编号 | 场景与输入                                                  | 预期行为                                                                   |
| ---- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| L5.1 | 一次提交 9 条长短混合的任务，长度从 1 到 777 字节，带保护区 | 全部任务 COMPLETED；数据与保护区正确                                       |
| L5.2 | 任务很少的短批次（例如单条 3 字节任务）                     | 短批次仍能完成；数据与保护区正确；没有任务停在 PENDING                     |
| L5.3 | 一次提交大量任务，跨多轮链式投递                            | 全部任务 COMPLETED；数据与保护区正确；没有任务因缺少完成信号而停在 PENDING |
| L5.4 | 释放 batch 后，在同一连接与注册区上再提交一批               | 再次提交成功且数据正确                                                     |
