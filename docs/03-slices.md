# 实验三：多请求与切片

**实验目标**　扩展 Engine，使其一次提交可以接受多条搬运任务，并把每条任务切成多个 WR 投递。任务的本地范围与远端范围可以位于任意偏移，长度可以任意。

**教材**　[2.6.6 SEND/RECV 的 Scatter-Gather](https://renfeng.org/RDMA101/02-programming-model/06-send-recv/)、[2.3.3 lkey 和 rkey 的区别](https://renfeng.org/RDMA101/02-programming-model/03-mr/)、[3.5.4 MTU 与分片](https://renfeng.org/RDMA101/03-internals/05-rc-reliability/)、[2.3.7 常见错误](https://renfeng.org/RDMA101/02-programming-model/03-mr/)

**前置**　完成[实验二](02-async.md)：Engine 已有后台 worker，`submit_transfer` 只接受请求，任务状态由 CQE 推进。

## 背景

实验一搬的是一段连续内存，实验二把它变成异步执行，但它们都默认"一次提交就是一段连续范围"。真实的数据往往不是这样：它散落在若干块内存里，每块在本地与远端各有一个位置，彼此之间没有规律。应用知道哪块对应哪块，把它们描述给 Engine。

### 一次提交，多条任务

一条任务描述一对连续范围：本地一段（`local_address`、`length`），远端一段（`remote_address`、同一个 `length`）。一个本地位置对应一个远端位置，这就是接口的基本单位。

数据散落在多少块内存里，就有多少对这样的范围。能不能把好几块远端位置并进一条任务？远端侧没有能装下它们的结构：一个 WR 的 `sg_list` 只描述本地内存——它虽然可以挂多个 SGE，把好几块不连续的本地内存拼进一次发送；但远端侧只有一个 `remote_addr` 和一个 `rkey`。每多一个远端位置，就多一组地址与 key，也就多一条任务。

### 一条任务，切成多片

一条任务的范围可以任意长。把它整段放进一个 WR 不是不行，但会让单次投递的粒度不可控：设备队列深度、单条 WR 的大小都有上限，Engine 需要在两者之间做权衡。于是每条任务会按一个内部切片大小切开，一片一个 WR 投出去。

切片推进的是地址：第 i 片的本地地址是"起始地址 + i × 切片大小"，远端地址同理。**推进地址，key 还是按 MR 查表。** `lkey` 属于本地 MR，`rkey` 属于该 peer 已导入的远端 MR 描述，它们标识的是"哪一块内存被授权"，而不是"这块内存里的第几个字节"。所以每片都按当前地址去注册表里查一次 key——本地与远端用的是同一套按区间查找的逻辑。由于一个请求的范围必须完整落在同一个注册区内，同一条任务的所有切片查到的其实是同一个 key。

切片大小不是 MTU。它决定 Engine 一次投递多少字节；超出 MTU 之后的分片与重组由网卡和 provider 负责（教材 3.5.4）。两者是不同的层次。

### "完成"的含义变了

到这里，两个粒度已经对不上：一次提交里有若干任务，一条任务里又有若干 WR。所以"一次提交"和"一次设备投递"不再是同一件事，一个 WR 完成也不等于任务完成——每片完成只推进这条任务的进度，所有切片都完成，任务才进入 COMPLETED。`get_transfer_statuses` 返回的是任务的终态，而不是某个 WR 的完成情况。

本实验先把范围映射与完成条件做对，允许同一时刻只有一片在途；在途多片由[实验四](04-window.md)处理。

## 实验内容

### 范围与边界

**实验边界：** 实验三只要求把一次提交从"一条任务"扩展为"一组任务"，并把每条任务切成多个 WR：任务的本地与远端范围可以位于任意偏移，长度可以任意。可以缩小为只处理一个 peer、一个存活 batch，并让 worker 逐片等待，即同一时刻只有一片在途。

本实验不要求在途多片：worker 可以等一片完成后，再投递下一片；这样也能处理远超 SQ 容量的总片数。[实验四](04-window.md) 再把逐片等待改为多条切片同时在途，并引入多个 batch。

**不在本实验范围内：** 多个 batch 并存与发送窗口（实验四）；批量投递与选择性信号（实验五）；错误 CQE 之后的重试或恢复。

## 实现要点

**1. 任务记录。** batch 保存任务集合，每条任务记录自己的切片进度、各片完成情况与终态。任务记录在提交时建立，不引用调用者的请求数组；`get_transfer_statuses` 一次返回全部任务，顺序与提交一致。

**2. 切片规则。** 对每条任务按内部切片大小切分，四条约束同时成立：覆盖原始范围（首片从起始地址开始，末片结束于"起始地址 + length"）；不重不漏（相邻片不重叠也不留空隙）；两个地址同步推进（每片的本地偏移与远端偏移相等）；每片长度不超过切片大小。长度不是整数倍以外的余数构成尾片，需要单独处理。

**3. 投递方式。** 沿用实验二的异步提交与 worker。本实验允许发送窗口为 1：worker 等一片完成后，再投递该任务的下一片，应用线程不参与等待。

**4. 任务完成条件。** 一条任务的全部切片完成，该任务才进入 COMPLETED；任一片失败则整条任务记为 FAILED。批内任务全部进入终态后，`free_batch` 才可以成功。

**5. 校验先于接受。** `submit_transfer` 必须先完成对整个请求数组的校验，再接受其中任何一条。若一边校验一边投递，非法请求位于数组后部时，前部的合法请求已经写入远端内存，此时返回"整批拒绝"与实际状态不符。

## 验收

实验三的验收围绕三件事：范围映射、切片选择，以及多任务 batch 的状态与生命周期。同一时刻只有一片在途的实现也可以通过；任务的完成顺序不作要求。

切片粒度由实现自己选，验收不作规定，只要求它能切开验收里最长的那条请求：`1 MiB + 17 B` 必须至少产生两个 WR，所以粒度要小于 1 MiB + 17 B（例如 16 KiB）。

实验三的测例会按下面的要求检查你的 Engine 行为：

| 编号 | 场景与输入                                                                                                     | 预期行为                                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| L3.1 | 一批 19 条 WRITE，长度不同，源与目标分别采用不同的离散布局                                                     | 全部任务完成；每段目标数据正确，源区与目标区的保护区不变                                                               |
| L3.2 | 分别提交 1 B、4 KiB、4 KiB + 1 B、64 KiB、64 KiB + 1 B、1 MiB、1 MiB + 17 B 的单任务 batch；起始地址带非零偏移 | 每批返回一个 COMPLETED；数据与保护区正确；最后一条请求实际拆成至少两个 WR，不遗漏尾部                                  |
| L3.3 | 一条合法请求后接一条远端范围越界的请求，同批提交                                                               | 整批返回 INVALID，不产生 batch，也不写入任何目标范围；随后仍能提交合法批次                                             |
| L3.4 | 提交五条长度不同的任务，传输期间反复查询状态，完成后再次查询                                                   | 未完成的任务为 PENDING；查询只读、不等待完成，各任务状态不回退；最终五条任务均为 COMPLETED，重复查询保持一致，数据正确 |
| L3.5 | 提交多任务 batch，仍有 PENDING 任务时调用 `free_batch`，全部任务完成后再次释放                                 | 未完成时返回 BUSY，batch 保持有效、可以查询；全部任务完成后释放成功，数据正确                                          |
| L3.6 | 释放 batch 后复用原连接与注册区，再新增注册区并提交新任务                                                      | 两轮搬运均成功；新增注册区可通过原连接使用，原有数据保持正确                                                           |
