# 实验四：发送窗口

**实验目标**　在多任务切片的基础上引入发送窗口：让多条 WR 同时在途，凭完成证据回收配额，并让多个 batch 共享同一份配额。

**教材**　[2.4.3 `ibv_qp_cap` 结构体](https://renfeng.org/RDMA101/02-programming-model/04-qp/)、[2.5.2 CQE 数量的选择](https://renfeng.org/RDMA101/02-programming-model/05-cq/)、[2.4.7 投递 Send 请求：`ibv_post_send`](https://renfeng.org/RDMA101/02-programming-model/04-qp/)

**前置**　完成[实验三](03-slices.md)：一次提交支持多条任务与切片，worker 逐片投递。

## 背景

实验三的 worker 已经能独立推进任务，不再需要应用查询状态来驱动。但它推进的方式是一片一片来：投一片、等它完成、再投下一片。应用线程不再被阻塞，瓶颈转到了传输侧——设备同一时刻只有一条 WR 可做，上一片不完成，下一片就投不出去。

### 空档来自"等上一片完成"

一条 WRITE 从投递到完成，要经过链路往返、对端处理和完成通知。这段时间设备并不是无事可做——只要还有待投递的切片，它完全可以先投出去。逐片串行时，设备在"上一片完成、下一片投递"之间空转；切片越多、每片越小，空档占的比例越大。要让它持续工作，就得让若干条 WR 同时在途。

### 在途 WR 要有一条上限

SQ 能容纳的 WR 有限，CQ 容量也有限；而应用一次提交的任务可能很多，每条任务又可能切成很多片，展开后的 WR 数很可能远超过这些限制。所以 Engine 不能一接受就把所有切片都投出去，而是让任务先待在软件队列里，只维持有限个 WR 在设备中。这个上限就是发送窗口（`window`），它统计的是整个 Engine 已投递、尚未凭完成证据回收的 WR 数量。

每投出去一条 WR，窗口里就少一个空位；每收到一条完成，就空出一个位置。还能再投几条，就是还剩多少**配额**。

**接受**和**投递**从此是两件事：接受表示任务已经归 Engine 管理，投递表示某个 WR 真的进了 QP。

### 配额凭完成证据归还

投递成功只说明 WR 进了发送队列，不说明设备已经搬完。所以配额只能凭 CQE 归还，任务状态也只能由 CQE 推进；"切片都投出去了"不能当作完成。

### 多个 batch 共用一个窗口

窗口属于整个 Engine，不专属于某个 batch。任何一个 batch 都不能独占它，也不能因为某个 batch 还没做完，就停下其他 batch 的完成回收和补投。

## 实验内容

### 范围与边界

**实验边界：** 实验四只要求把逐片等待改为受发送窗口约束的投递：只要还有配额，就继续投递后面的切片；CQE 到达后归还配额并补投。可以缩小为单个 peer、单个后台 worker、单个 CQ。

本实验不要求批量投递：每次投递一条 WR 即可，把多个 WR 连成链表一次投递由[实验五](05-batching.md)处理。

**不在本实验范围内：** 批量投递与选择性信号（实验五）；错误 CQE 之后的恢复、重试与重连；多 QP、多 CQ、多后台 worker。

## 实现要点

**1. 在途记账。** 维护已投递且未凭完成证据回收的发送 WR 计数，配额不足时不投递新的切片。

**2. worker 的循环。** 循环由三个动作构成：回收完成、归还配额、投递后续切片。

```
while (running) {
    poll_completions();   /* 回收 CQE，推进任务状态，归还配额 */
    dispatch();           /* 对仍有剩余工作的任务投递下一片 */
}
```

`dispatch` 在投递前检查剩余配额；配额不足时跳过该任务并继续处理其他任务，这里不要求特定的公平调度算法。

**3. 配额归还以完成证据为依据。** 只有 CQE 才能归还配额、推进任务状态。投递成功不等于传输完成，不得以"所有切片均已投递"作为配额归还或任务完成的依据。

**4. 区分投递进度与完成进度。** 一条任务可以已经投递多片，但只完成其中一部分。worker 持续处理 CQE 并按剩余配额补投，不能每投递一片就等待该片结束。

**5. 多个 batch 并存。** 多个 batch 共享发送配额。不能因等待某个 batch 整体完成，就停止处理其他 batch 的 CQE 或可投递的工作。

**6. 任务与批次的终止。** 一条任务的全部切片完成后才进入 COMPLETED；批内任务全部进入终态后，`free_batch` 才成功，回收后的任务记录应可被新的提交复用。

## 验收

实验四的验收既看搬运结果，也看发送窗口是否真的生效：有多条 WR 待投递时，同时在途的 WR 至少达到两条；任何时刻在途的 WR 都不超过 QP 的发送队列容量；任务全部完成时，投出去的每一条 WR 都已有完成证据。

窗口取多大由实现自己决定。

实验四的测例会按下面的要求检查你的 Engine 行为：

| 编号 | 场景与输入                                                      | 预期行为                                                                   |
| ---- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| L4.1 | 一个 batch，共 1024 条任务，长度不一                            | 全部任务 COMPLETED；逐任务数据与保护区正确                                 |
| L4.2 | 两个 batch，各 512 条任务，交错推进                             | 两个 batch 的逐任务终态、数据与保护区正确；任一 batch 未完成时不阻塞另一个 |
| L4.3 | 任务总片数远超设备 SQ/CQ 容量（例如 1024 条任务、每条多次切片） | 全部任务最终完成，不因 SQ/CQ 容量报错或丢任务                              |
| L4.4 | 两个 batch 都终态后释放，再用同一连接与注册区提交新任务         | 两个 batch 的 `free_batch` 都成功；释放后再次提交成功且数据正确            |
| L4.5 | 在配额不足、多个 batch 竞争的情况下持续运行到结束               | 没有死锁、没有任务永久停在 PENDING；所有任务最终进入终态                   |
